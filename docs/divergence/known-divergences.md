# 标准与实现已知差异登记

首批条目随 2026-09-24 正文对齐阶段写入。每条差异可从当前仓库复核；一次性审计过程不进入本表。

| 编号 | 主题 | 标准侧 | 实现侧 | 影响 | 策略 |
| --- | --- | --- | --- | --- | --- |
| D1 | 搜索与流程入口命名 | [搜索流程](../flows/search-flow.md) 的 `SearchRequest` / `SearchResultSink` / `SearchSourceStatus`（含 `stale`、`storage-error`），[阶段 C](../implementation/phase-c-workflows.md) 历史名 `searchOne` / `searchMany`，[阶段 D](../implementation/phase-d-extended-capabilities.md) 历史名 `searchOne` / `explore` / `getBookInfo` / `getChapterList` / `getContent` | `packages/source-core/src/index.ts` 导出 `searchBooks` / `discoverBooks` / `loadBookDetails` / `loadTableOfContents` / `loadChapterContent`，输入为 `SearchInput` 等，输出 `RuntimeResult` | 标准与流程文档中的入口名不能直接 `grep` 到代码；集成方按文档实现会失败 | 代码为准；文档已标注历史/目标名。若未来补齐多源 `searchMany` 或统一门面，先改代码再改标准 |
| D2 | 端口与宿主门面命名 | [宿主接口](../implementation/runtime-host-interfaces.md)、[阶段 B](../implementation/phase-b-rules-request.md) 的目标 `RuntimeHost` / `CallContext`，[目标 `OperationResult`](../implementation/runtime-contracts.md)（含 `stale` / `unknown` / `effects` / `changes` / `cleanup`） | `WorkflowPorts` / `ReadingPorts` / `NetworkHost`；Node 侧 `SourceRuleHost` / `SourceRequestHost` / `QuickJSJavaScriptHost` 等；流程结果为 `RuntimeResult<T>` + `WorkflowStatus`（无 `stale` / `unknown`） | 按 `OperationResult` 或 `RuntimeHost` 写适配层会类型错误；部分流程文档（[正文](../flows/content-flow.md)、[校验](../flows/source-check-flow.md)）仍描述目标保存 token 与 `checkSources` | 目标契约保留在 `runtime-contracts.md` / `runtime-host-interfaces.md` 并显式标注；新集成只依赖 `package-usage.md` |
| D3 | 能力清单中过时的“未实现”行 | [兼容矩阵](../quality/compatibility-matrix.md) 部分行仍写“未实现 runtime，待 fixture” | 导入/规则/请求/四类读取流程等已有实现与自动测试（`packages/source-core/tests/`、`packages/source-node/tests/`） | 读者可能把已实现但未跑 Android golden 的项误判为完全缺失，或把“已有实现”误判为“已验证兼容” | 已实现行改为“实现见 source-core/source-node…对照 fixture 待执行”；未实现能力（见 D4）保持未实现表述 |
| D4 | 尚未实现的公开能力 | [能力清单](../standard/capability-inventory.md)、[包使用](../implementation/package-usage.md)、[批量正文](../flows/content-flow.md)、[校验流程](../flows/source-check-flow.md) | `packages/` **没有** `checkSources`、`getContentBatch`、`searchMany`、`SourceApplicationService`、`SourceRepository`、`SecretStore`、`JobStore`、段评结构化读取、WebView/`@webjs`、付费与事件协议 | 标准与流程可描述完整目标，但调用当前 package 无法完成检测、批量正文或应用侧持久化 | 标准侧保留完整承诺；实现侧不导出即为 `capability-missing` / 文档显式“尚未实现”。进度见能力清单与阶段 D |
| D5 | Android 独立登录凭据头尚无 TS 对应能力 | [URL 与请求规则](../standard/url-request-rules.md#5-cookie-登录凭据和重定向) 描述 Android 登录头同站规则 | Android 单独保存并注入登录凭据头；TS 当前 `source.header` 是普通书源 Header，没有独立 SecretStore / 登录头模型 | 把 `source.header` 当成全部登录凭据会误删 Referer、User-Agent 等正常配置；也不能声称 TS 已按同站范围保护登录令牌 | 当前保留普通 source header，不做全量跨域剥离；缺少的独立登录凭据能力按宿主边界登记。Android 只检查初始 URL，TS 没有该自动注入路径 |
| D6 | 默认 User-Agent 来自平台配置 | Android `BaseSource.getHeaderMap()` 在未配置时使用 `AppConfig.userAgent` | TS 核心可读取 `NetworkHost.defaultUserAgent`，Node 可从 `NodeNetworkOptions.defaultUserAgent` 配置；省略时由 HTTP 客户端决定 | 同一份书源在不同 Node 客户端上可能携带不同默认 UA，不能把客户端默认值描述成 Android 默认值 | 应用可通过网络宿主显式提供默认 UA；书源 Header 和 URL options 仍按各自优先级覆盖，不在核心硬编码 Android 全局配置 |
| D7 | `concurrentRate` 尚未覆盖完整 Android 生命周期 | Android `ConcurrentRateLimiter` 含首个非法配置 fallback 与 `ajaxAll(..., true)` bypass | TS `SourceRateLimiter` 覆盖普通请求固定窗口、取消和 `putConcurrent` 有效更新；缺首次非法配置诊断、Java bridge bypass 与源编辑/删除清理入口 | 个别 Android 脚本批量请求的限流次数或非法配置处理可能不同 | 标为部分实现；保留逐项 fixture，不因已有固定窗口实现而宣称完整兼容 |
| D8 | HTTP 传输策略保留 TS 安全限制 | Android 请求路径允许其网络栈支持的请求目标 | TS RequestPlan 限定 HTTP(S)，Node 默认拒绝环回、私网和链路本地地址 | 本地调试书源或非 HTTP(S) 目标在 Node 侧会被拒绝 | 作为宿主部署安全策略保留，不为 Android parity 关闭 SSRF/协议限制；见[部署边界](../operations/runtime-security-and-deployment.md) |
| D9 | bridge 子请求不重跑动态 source header | Android `AnalyzeUrl` / `BaseSource.getHeaderMap()` 的 Header 脚本行为 | TS `SourceRequestRuntime` 对 nested JavaScript bridge 请求跳过动态 `source.header`，静态 header 仍使用 | Header 脚本内调用 `java.ajax` 不会在 TS 子请求上重新生成动态头；去除该保护又可能形成递归请求 | 作为当前防递归限制保留；需要变更时以 Android 实际重入路径和有界递归 fixture 决策 |
